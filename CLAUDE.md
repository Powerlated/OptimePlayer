## Overview

Optime Player emulates retro console sound systems and plays their sequenced music in real time:

- **Nintendo DS** — loads `.nds` ROMs or standalone `.sdat` sound archives, parses the SDAT container, and synthesizes the SSEQ format. The engine logic comes from the reverse-engineered pokediamond project (https://github.com/pret/pokediamond).
- **Game Boy Advance** — loads `.gba` ROMs running the MP2K ("Sappy" / `m4a`) engine, locating the song table by code signature or heuristic scan. The engine logic comes from the pokeemerald decompilation (https://github.com/pret/pokeemerald), cloned locally at `~/Git/pokeemerald` for reference.
- **DSE (Procyon Studios)** — the SMDL (sequence) + SWDL (sample/instrument bank) formats used by *Pokémon Mystery Dungeon: Explorers of Sky*. The engine logic comes from the pmd-sky decompilation (https://github.com/pret/pmd-sky), cloned locally at `D:\Git\pmd-sky` (which also ships the extracted `files/SOUND/BGM/*.smd`/`*.swd` music). A full `SoundData`/`DevicePlayer` backend (`devices/dse/`): parsing + sample decoding, the SMDL sequencer, the volume envelope, and the ROM-exact note→frequency and square-law volume transcribed from the voice-update assembly. A PMD `.nds` ROM (no SDAT) is identified by the `swdl`/`smdl` scan and plays through the same pipeline as the other consoles.

The project is a **Rust workspace** with an `egui`/`eframe` UI that runs both natively and on the web (wasm). Synthesis accuracy is anchored to the pret decompilations (pokediamond for DS, pokeemerald for GBA), verified by Rust unit tests transcribed from the C — not by parity with the original JavaScript app, which is preserved verbatim under `legacy-js/` (see "Legacy app" below) purely as a historical reference.

## Commands

The workspace pins **nightly Rust** (`rust-toolchain.toml`): the default `simd` cargo feature uses `std::simd` (portable SIMD) in the sinc resampler. `--no-default-features` on `optime-core` builds the scalar gather (works on stable). `.cargo/config.toml` sets `-C target-cpu=native` for native x86-64/aarch64 hosts — the hot path relies on AVX2/FMA codegen — and `--cfg=web_sys_unstable_apis` for the `wasm32-unknown-unknown` target so the web build can use the browser Media Session API (web-sys gates it behind that cfg).

- `cargo run -p optime-app` — run the native desktop app (loads a demo from `demos/` on start)
- `cargo test --workspace` — run all tests (unit + integration + pret-reference transcription tests)
- `cargo clippy --workspace --all-targets` — lint (kept warning-clean)
- `cargo fmt --all` — format
- `cargo clippy -p optime-app --target wasm32-unknown-unknown` — type-check the web build
- Web dev server: `cd crates/optime-app && trunk serve` (needs `rustup target add wasm32-unknown-unknown` and `cargo install trunk`)
- Web release build: `cd crates/optime-app && trunk build --release`

The web app deploys to GitHub Pages via `.github/workflows/deploy.yml` (Trunk release build with `--public-url "/<repo>/"` → Pages artifact). It triggers on pushes to `rust-rewrite`/`master`. The same workflow also stages the legacy browser app (see "Legacy app") into `dist/legacy-js/` so it is served alongside the Rust app at `/<repo>/legacy-js/`: it copies `legacy-js/` verbatim plus only the shared resources the legacy app loads relative to itself — `fonts/`, the three `assets/piano_section_*.png`, and the six `demos/*.sdat` its demo buttons reference (not the whole `demos/` dir, which carries large `.zip`/`.gz`/`.gbaaudio` files the legacy app can't use).

### Local-only extras

`crates/optime-app/build.rs` generates optional, **local-only** "extras" from a gitignored `local_extras.txt` manifest: curated song-name tables keyed by source filename (`JSONS_BY_GAME_FILENAME`) and extra demo entries (`LOCAL_DEMOS`), emitted into `OUT_DIR` and `include!`d by `song_names/mod.rs` and `app.rs`. This lets a personal checkout carry ROM-hack metadata (titles + a demo archive, kept under the gitignored `src/song_names/local/` and `demos/*.gbaaudio.gz`) that is never committed. With no manifest the generated tables are empty and the app builds byte-for-byte like a clean clone. Manifest lines (`#` comments and blanks ignored), `|`-separated: `table|<source-filename-key>|<json-under-src/song_names>` and `demo|<label>|<demo-stem-under-demos>`.

Two `optime-core` examples back offline rendering (both take an already-decompressed archive — gunzip any `*.gbaaudio.gz` first): `render_songs` (`cargo run -p optime-core --example render_songs -- <archive> <out_dir> [seconds]`) renders every playable song to a mono WAV plus a `manifest.json`; `export_album` (`--example export_album -- <archive> <names.json> <out.flac> [--max-silence S] [--limit N]`) renders the songs named by a curated song-name JSON, in album order, with each console's high-quality preset (the shared `LoopAndTransitionOptions::export` controller policy: fade after one loop — with a 90s after-loop cap for long-looping tracks — then a 3s fade), into a single stereo FLAC normalized album-wide to -16 LUFS (EBU R128). Each track's leading/trailing near-silence is trimmed and a fixed `--max-silence` gap (default 0.8s) is inserted between songs, so the dead air between tracks is capped at that length. All three phases are parallel: the render fans out across CPUs into per-track temp PCM files (one live progress bar per worker); the analyze phase measures each track on its own `EbuR128` via rayon and combines them with `loudness_global_multiple` (integrated loudness gates out the inter-song silence, so per-track == whole-album); the encode feeds tracks serially but compresses channels in parallel via flac-codec's `rayon` feature. Memory stays bounded regardless of album length. Uses `flac-codec` (rayon) + `ebur128` + `clap` + `indicatif` + `rayon` (optime-core **dev-dependencies** — the lib itself stays dependency-light). `export_album` also carries a `--benchmark [PCT]` mode that renders a deterministic, evenly-spread `PCT` of the album (no FLAC/temp files) and reports the median of 3 timed passes; both it and the FLAC render share the one `parallel_render` code path. **THE render-performance benchmark** is `export_album --benchmark 3%` on Mother 3 (`demos/mother-3.gbaaudio` + `crates/optime-app/src/song_names/mother_3.json`), fixed at 4 threads — see `docs/sample-width-benchmark.md` (which found narrowing `Sample` f64→f32 gives no measurable speedup).

## Architecture

Two crates. The core's data flow is a strict pipeline — each device parses its own formats and emits one **standardized event stream**; the synthesis layer knows nothing about any console:

```text
ROM / archive bytes ─► devices::SoundData          (per-console parsing: songs, instruments)
SoundData + song id ─► devices::DevicePlayer       (per-console sequencer + envelope model)
DevicePlayer::tick  ─► devices::SynthEvent stream  (the standardized message set)
SynthEvent stream   ─► SynthController             (voice pools, master clock, mixing)
```

### `crates/optime-core` — the platform-independent engine (no browser/UI/audio deps)

Pure-`std`. Top-level modules are the console-agnostic synthesis layer; everything console-specific lives in a folder under `devices/`.

**`devices/`** — one folder per console, plus the shared interface:

- `devices/mod.rs` — the device interface as two **object-safe traits** (dynamic dispatch; no console-specific methods leak into them). `SoundData` (`song_ids` — only playable songs are listed; `make_player` → `Option<Box<dyn DevicePlayer>>`; provided defaults `song_name` → `None`, `waveform_dc_stats` → empty; `as_any` for downcasts; and a provided `song_length_seconds` that runs the player headless), implemented per console in each `devices/<console>/`. `load_all(bytes) -> Vec<Box<dyn SoundData>>` is a free function (probes NDS → DSE → GBA). `WaveformDcStat` (one decoded waveform's `label`/`dc_shift`/`length`/`sample_rate`). `DevicePlayer` (`clock_rate`, `cycles_per_tick`, `steps_elapsed`, `step_rate`, `steps_per_beat`, `tick`, provided `tick_rate`). Anything console-specific (a GBA ROM's `game_code()`/`extract_audio()`) is reached by `data.as_any().downcast_ref::<GbaRom>()`, never by a trait method.
- `devices/messages.rs` — the standardized stream: `SynthEvent` (`NoteStarted`, `VoiceVolume`, `VoicePitch`, `VoiceDetune`, `VoiceStopped`, `NoteReleased`, `TrackPan`, `TrackDetune`, `Looped`, `Ended`), `VoicePitch` (`Midi {note, sample_pitch_hz}` for repitched samples vs `DataRateHz` for register-driven rates), `VoiceId` (monotonic `u64`), `TickFeedback` (synth-side voice endings reported back to the device each tick).
- `devices/nintendo_ds/` — `sdat.rs` (the `Sdat` parser: SYMB/INFO/FAT/SBNK), `bank.rs` (`InstrumentBank`, ADSR coefficient helpers), `sequence/` (the SSEQ bytecode interpreter: `track.rs`, `message.rs`, `interpreter.rs`, `mod.rs` with the 16 tracks / message queue / `SND_CalcRandom`), `tables.rs` (DS BIOS / pokediamond lookup tables, bit-identical), `volume.rs` / `lfo.rs` (decibel-domain channel volume and LFO math, pokediamond ports), and `player.rs` (`NdsPlayer`: decodes the linked SWAR sample archives up front, runs the sequencer behind the BPM timer, owns per-note ADSR/LFO state, emits `SynthEvent`s).
- `devices/gba/` — `rom.rs` (`GbaRom`: song-table location via the `m4aSongNumStart` signature with a brute-scan fallback, `SongHeader` parsing), `voice.rs` (`ToneData` / voicegroup resolution incl. key-split and rhythm voices, `WaveData`), `sequencer.rs` (`Mp2kSequencer`: the MPlayMain track interpreter — runs per VBlank frame, `tempo_c += tempo_i; while >= 150` steps, emits `Mp2kOp`s), `tables.rs` (`gClockTable`/`gScaleTable`/`gFreqTable`/CGB/noise tables + `MidiKeyToFreq`/`MidiKeyToCgbFreq`, bit-identical), `player.rs` (`GbaPlayer`: DirectSound + 4 CGB channel allocation/stealing, per-frame envelopes incl. pseudo-echo, generated square/wave/noise sample data, emits `SynthEvent`s; the pan-law agreement with the controller is pinned by `pan_law_composition_matches_per_side_envelopes`. `dc_center` always centers the generated PSG waveforms, and — when the per-device `remove_sample_dc_offset` setting is on (off by default; the cache is keyed by the flag so toggling re-decodes) — also subtracts each DirectSound PCM sample's DC offset to match the GBA's AC-coupled output and stop the envelope on/off thump), and `extract.rs` (`extract_audio`: the audio-only ROM image — a static walk of the track bytecode, voicegroups, and wave data zeroes everything the MP2K engine can't reach, keeping offsets so playback is bit-identical; exposed as the app's "Export GBA audio data" button and the `extract_mp2k` example; also `waveform_dc_stats`, which walks a song's voicegroup (DirectSound waves only, key-split/rhythm sub-groups followed) and decodes each to report how far it was DC-shifted, sorted most-shifted first — backs `SoundData::waveform_dc_stats`).
- `devices/dse/` — the full DSE backend (`DseSoundData`/`DsePlayer`, a `SoundData`/`DevicePlayer` implementation): `swdl.rs` (`Swdl`: the SWDL bank parser — 0x50-byte header + 0x10-aligned `wavi`/`prgi`/`kgrp`/`pcmd` chunks; `WaveformInfo` WAVI entries decoded to `Waveform` via the shared PCM8/PCM16/IMA-ADPCM decoders; the game's main bank `bgm.swd` holds the `pcmd` data, per-song `bgm####.swd` hold `prgi` programs referencing it), `smdl.rs` (`Smdl`: the SMDL sequence parser — `song` chunk TPQN + 4-byte-aligned `trk ` chunks), `events.rs` (the SMDL track bytecode: `decode_track` + the opcode/operand table transcribed **from the pmd-sky decomp assembly** — `SMD_EVENTS_FUN_TABLE` and each `DseTrackEvent_*` handler's pointer advance in `asm/main_0206C9BC.s`/`lib/DSE`, plus the `ParseDseEvent` PlayNote bit layout and the `_020B0B7C` pause LUT), `sequencer.rs` (`DseSequencer`: the multi-track SMDL interpreter — pauses, sub/main loops, tempo, emitting a flat `SeqOp` stream), `envelope.rs` (`SoundEnvelope`: the `dc_envelope.c` volume slide), `pitch.rs` (`note_key_to_hz`: the ROM-exact note→frequency — the split's `key_base`/`note_delta`/key form an 8.8-semitone `note_key` fed through the bit-identical `_020B1310`/`_020B1394` pitch tables to the absolute PCM playback rate in Hz, since the WAVI `sample_rate` is unused at runtime; `0x00FFB0FF` is the NDS sound clock), `volume.rs` (the `DseVoice_*` integer volume chain — `velocity*program*split/127²` note volume, `track*expr/127` channel volume, and the `(env*vol*note/8032)²>>9` **square law**, magic-divisions transcribed bit-for-bit), `lfo.rs` (`Lfo`: the channel LFO engine — vibrato/tremolo/auto-pan — transcribed from `dc_lfo_1.s`/`dc_lfo_2.c`: the eight `SoundLfoWave_*` waveforms, `SoundLfoBank_Set` construction (depth/period/fade-in), and `SoundLfoBank_Tick`, routed to pitch/volume/pan exactly as `DseVoice_UpdateParameters` applies them), and `player.rs` (`DsePlayer`: decodes samples on demand, runs the sequencer behind the ~100 Hz driver tick, drives one `SoundEnvelope` per voice, plus the **pitch-wheel key bend** (`SetKeyBend`/`SetKeyBendRange` → a `TrackDetune` of `range*value/8192` semitones, the dominant Explorers pitch effect) and per-note pitch/volume LFOs + a track auto-pan LFO; emits `SynthEvent`s via `VoicePitch::DataRateHz`). Proven end-to-end by the `dump_dse` example (decode spike + a ROM-mode `SoundData`/`DevicePlayer`/look-ahead run, plus an effect-event tally) against `D:\Git\pmd-sky\files\SOUND\BGM`. Not yet modelled: `SongVolumeFade`, per-note pan, tuning jitter.

**Synthesis layer** (console-agnostic):

- `synth_controller/` — `mod.rs` (`SynthController`: owns two per-track synthesizer sets — the output-rate set and the mixer-rate set — plus their `slot_owner` bookkeeping (shared set-agnostic free fns: `render_set`/`find_slot`/`cut_finished`), the master clock, `next_sample`/`fill`/`tick`, applies `SynthEvent`s and feeds `TickFeedback` — voice steals and one-shot sample endings — back to the device. It also owns the **single shared end-of-song fade**: a caller sets a `LoopAndTransitionOptions` policy (loops-before-fade / too-long-after-loop-threshold-seconds / fade-on-end / grace-seconds / fade-seconds; presets `none`/`export`/`live`) via `set_loop_and_transition` — or triggers an immediate ramp with `request_transition(fade_seconds)` — and the controller counts loops, applies the one linear fade gain to its own `next_sample`/`fill` output, and pumps `PlaybackEvent`s (`Looped`/`TransitionStarted`/`Finished`) the caller drains with `take_messages`. This is the lone home for fade/loop policy, shared by live playback (`audio.rs`) and both offline exporters (`render_to_samples`, the `export_album` example); the default `none` policy never fades, so plain renders (visualizer/tests) are unaffected. With the config's `use_mixer` set, sampled (non-PSG) voices play on the mixer set at `mixer_sample_rate` and PSG voices on the output set; the controller *routes* the mixer set's stereo bus into the `Bank` (which owns only a `StreamResampler`, not the synths) to upsample it to the output rate, while the output set sums straight through; off, every voice plays on the output set — bit-identical to the single-set engine), `config.rs` (the standalone option types that make up the config struct: `PopSmoothing { psg, sample, slew_seconds }` — a per-kind de-click gain slew whose ramp time is user-adjustable (`DEFAULT_POP_SLEW_SECONDS` = 2 ms), applied in every resampling mode — the `DelaySmoothing` policy for the stereo expander's delay-length changes, and `HighShelf`. The config struct itself is `PerDeviceSettings` (`device_settings.rs`, see below), consumed directly by the synthesis layer via its resolver methods — `resample()`/`mixer_resample_mode()` → `InstrumentResampleMode`, `tuning()` → `TuningSystem`, `pop_smoothing()`, `delay_smoothing()` — plus its `smooth_pan` (slew the L/R pan gain split to de-click pan jumps, orthogonal to the delay-length `DelaySmoothing`), `use_mixer`/`mixer_sample_rate`/`track_enables` fields and `psg_crunch_compensation` — a **per-rate** RBJ low-pass cascade (in `mod.rs`: order/cutoff-Hz/Q constants fit by `scripts/fit_compensation.m` to the measured nearest→crunch HF power loss on real DirectSound, rebuilt via `BiquadFilter::low_pass` on any output-rate change so the knee stays at a fixed frequency) that colours the PSG/output-set bus with the same high-frequency rolloff the mixer-to-output **crunch** gives DirectSound, so PSG voices don't sit too loud; only runs when `use_mixer` is set and `mixer_resample` is the output-Nyquist crunch), `vis.rs` (`FsVisController`: a parallel look-ahead runner for visualizers, no audio — it runs a second `Box<dyn DevicePlayer>` headlessly and extracts `VisNote`s from the standard `SynthEvent` stream (`NoteStarted`/`NoteReleased`/`Looped`/`Ended`), so it is fully device-agnostic and never reaches into a device's sequencer; the live `tick` and the whole-song `overview` share the note/duration bookkeeping).
- `synth/` — `instrument.rs` (`WaveformInstrument`, one voice: `VoicePitch`-driven frequency, resampling, pop-smoothing gain slew via a `Slewer`, block rendering; `advance`/`advance_block` share the `fold_pos` loop-fold helper), `synthesizer.rs` (`WaveformSynthesizer`: round-robin voice pool, pan (the L/R gain split optionally slewed by a `Slewer` under `smooth_pan`), Haas widening with optional held delay changes, bass-mono crossover), `delay_line.rs` (`DelayLine`). All resampling lives in `resample/` (below); `synth` consumes it through `crate::dsp::resample::{gather_sinc, …}`.
- `resample/` — windowed-sinc resampling: `kernels.rs` (FIR kernel/response, `ResampleTables`), `gather.rs` (SIMD/scalar gather kernels), `source.rs` (the loop-aware source-staging gather `gather_sinc`/`GatherSource` that feeds a voice), `stream.rs` (`StreamResampler`: the continuous fixed-ratio stereo resampler for the mixer-bus → output stage; applies any `InstrumentResampleMode` reusing the same `resample_sinc` gather), `plan.rs` (`effective_gather`/`sinc_fc`/`mode_half_taps`: resolving an `InstrumentResampleMode` into the concrete gather + cutoff, shared by the voice gather and the stream resampler), `mod.rs` (public API).
- `waveform.rs` — `Waveform` (a decoded waveform + playback metadata), the `Sample` (`= f64`, one signal-path amplitude) and `Frame` (`= (Sample, Sample)`, a stereo pair) type aliases, `InstrumentResampleMode` (`NearestNeighbor`, `Linear`, clean `SincSampleNyquist`, crunchy `SincOutputNyquist` with per-kind PSG/sampler cutoff sliders), + `decode_pcm8`/`decode_pcm16`/`decode_adpcm`/`decode_wav`.
- `dsp/` — `biquad_filter.rs` (`BiquadFilter`, cascaded biquads), `slewer.rs` (`Slewer`: a reusable linear slew — holds a value and moves it toward a target by a bounded per-sample step, landing exactly; the shared building block behind the pop-smoothing gain ramp and the pan slew), `resample/` (above). `tuning.rs` — `midi_note_to_hz` (equal temperament / Pythagorean `TuningSystem`). `util.rs` — `read_u8/u16/u32` (return 0 on OOB), `search_for_sequence`, `CircularBuffer<T>`.

Runtime options are a `PerDeviceSettings` struct (`device_settings.rs`) threaded into the synthesis calls — there is no global state. It is both the app's serializable per-console settings *and* the engine's runtime config: settings-level choices (resampling-algorithm enums, tuning index, cutoff/tap sliders) are turned into the concrete values the engine wants by resolver methods on the struct, so there is no separate "resolved config" type.

**The master clock** lives in one place: `SynthController::next_sample` accumulates the device's `clock_rate()` per output sample and ticks the player every `cycles_per_tick() * sample_rate` cycles. For the DS that is `DS_CLOCK_RATE` (33,513,982) / `CYCLES_PER_TICK` (64 × 2728) ≈ 192 Hz with the BPM timer `+= bpm` / `while >= 240` inside the player; for the GBA it is `GBA_CLOCK_RATE` (16,777,216) / `CYCLES_PER_FRAME` (280,896) ≈ 59.73 Hz VBlanks with the `tempo_c` accumulator inside the sequencer. `SynthController::fill` renders in tick-aligned blocks, bit-identical to the per-sample path (pinned by `tests/block_render.rs`). The visualizer timeline is *sequencer steps* (DS: SSEQ ticks; GBA: tempo steps), converted to wall time via `step_rate()`.

### `crates/optime-app` — the eframe/egui front-end (native + web)

- `song_names/` — curated, human-readable song titles + official-soundtrack ordering for games whose ROMs carry no song names (kept in the app, not the engine, as cosmetic presentation metadata). Each game's table is a JSON file (`[{ "songId", "title" }]`) embedded via `include_str!` and parsed with `serde_json`; an entry's **array index** is its listing order. `mod.rs::lookup(filename, game_code, song_id)` resolves a table by the loaded source filename first (`JSONS_BY_GAME_FILENAME`, for DS / game-code-less games), then by GBA game code (`JSONS_BY_GBA_GAME_CODE`) — `pokemon_emerald.json` (`BPEE`, Super Music Collection titles generated against pret/pokeemerald `songs.h`, album-tracks-first) and `mother_3.json` (`A3UJ`, the MOTHER 3 fan translation's Sound Player names from its `musicnames.txt`, paired with each track's real MP2K song id via the ROM's Sound Player slot→song-id table — the player's order is *not* song-id order). The returned title **wins over** any ROM-embedded name. That drives the **Default** sort: curated songs first in that order, then the rest in native order (see `Song::ost_order` / `apply_sort` in `app.rs`). A native-only maintainer dev-tool — the **"Edit song names"** toggle at the bottom of the settings panel — turns the library list into an inline title/order editor (`song_edit_list_ui` in `app.rs`: rename, ▲/▼, drag-to-position) whose "Save to JSON" writes back to the source-tree file (`source_json_dir` from `CARGO_MANIFEST_DIR` + `target_filename`), baked in on the next build. Only the **curated** songs are written — those already in the loaded table plus any renamed/reordered this session (`Song::curated`), so untouched ROM-named songs stay out of the file; a brand-new game writes a derived filename that must be hand-wired into the `JSONS_BY_*` `const`s to load.
- `persisted.rs` — persistent user library (`TrackRef`, `Playlist`, `Library`, `RepeatMode`), the per-device `PerDeviceSettings` (resampling, stereo/mixer, shelf EQ, tuning — one each for `nds`/`gba`; re-exported from the core's `device_settings.rs`, which is where it lives and resolves into the engine's runtime values), and the `Persisted` bundle saved to eframe storage. All out-of-the-box user defaults live in the engine as named presets — `PerDeviceSettings::high_quality_nintendo_ds()` / `high_quality_gba()` in the core's `device_settings.rs` — which `Persisted::default` just calls (so offline tools like `export_album` share the exact app defaults); the core's `PerDeviceSettings::neutral()` is a separate engine-neutral baseline (every effect off) for tests/examples. The sub-structs intentionally have no `Default` impls. (`TrackRef::song_id` is the song id for any device; it serializes as `sseq_id` via `#[serde(rename)]` for storage/URL compatibility.)
- `audio.rs` — `AudioEngine`: a `cpal` f32 output stream (native + WebAudio) pulling from shared state. The callback's `step_playback` owns advancement: it drains the UI's `PlaybackCommand`s, asks the controller for a quick fade before a manual switch (`request_transition`) and installs the `live()` fade policy on each freshly decoded song, then watches for the controller's `Finished` `PlaybackEvent` (loop-count / FINE / requested fade reaching silence) and once silent **advances the index and decodes the next song right there** (the decode stall is inaudible because the output is already silent) and installs it — so playback keeps moving even when the UI's `update()` is frozen. The end-of-song fade ramp itself lives in the controller, not here; `GainRamp` only applies the master volume, the song fade-*in*, and the pause ramp.
- `media_controls.rs` — media-transport integration so Bluetooth/keyboard/lock-screen media keys — e.g. AirPods double-tap to skip, or a phone's lock-screen transport — drive playback. Native uses `souvlaki` (Windows SMTC / macOS Now Playing / Linux MPRIS), getting the window `HWND` from the `eframe::Frame` (`raw-window-handle`) and routing `MediaControlEvent`s through a channel. The web build uses the browser **Media Session API** (`navigator.mediaSession`): per-action JS closures push `MediaAction`s into an `Rc<RefCell<…>>` queue and call `ctx.request_repaint()` so a key press is applied on the next frame even while the UI idles. Both expose the same `MediaControls::new(ctx, frame)` / `poll` / `set_now_playing`; the app drains them each frame in `handle_media_controls` (`app.rs`) and pushes the current title/playback state back as "now playing". The Media Session types are gated behind web-sys's `web_sys_unstable_apis` cfg (set for the wasm target in `.cargo/config.toml`).
- `player.rs` — `AudioState` shared between the UI and the audio callback via `Arc<Mutex<…>>` (pause/fade/volume ramps, DSP-load stats), the audio-thread-owned `Playback` (the `PlaylistEntry` list + `index` + `repeat` + the command queue + `status_gen`, with `manual_step`/`auto_advance` as the unit-tested advance logic), the `PlaybackCommand` message set, and `render_to_samples` (offline WAV-export render: it sets the controller's `export()` fade policy and stops on the `Finished` `PlaybackEvent`, applying only the 0.5 export headroom — the loop/fade logic is the controller's).
- `visualizer.rs` / `piano_roll.rs` — procedural 16-track × 88-key piano roll drawn with `egui::Painter` (no image assets; original PNGs remain in `legacy-js`). Driven by `VisSnapshot` (`steps` + `step_rate`) and the `FsVisController` look-ahead.
- `theme.rs` — egui style/typography (Inter/SF Pro).
- `filter_plot.rs` — frequency-response plot for the resampler/crossover settings UI.
- `wav.rs` — minimal 16-bit PCM WAV encoder.
- `web.rs` (wasm only) — browser download + demo fetch helpers.
- `main.rs` / `lib.rs` — native window entry; on wasm mounts onto `#the_canvas_id` (see `index.html`, built by Trunk).

The config (`PerDeviceSettings` for the current song's console, with the live piano-roll track mutes injected as `track_enables`) is cloned each frame and pushed into the audio thread under the lock; the same lock is used to snapshot `notes_on` for the visualizer.

## Testing

- `crates/optime-core/tests/sdat.rs` — parses the real `demos/*.sdat` archives.
- `crates/optime-core/tests/gba.rs` — end-to-end MP2K test against a synthetic in-memory GBA ROM (table scan, sequencer, player, audio output, look-ahead).
- `crates/optime-core/tests/block_render.rs` — pins `SynthController::fill` bit-identical to the per-sample path.
- **pret-reference unit tests** — the accuracy anchor. Synthesis math is validated by transcribing the relevant C function from `pret/pokediamond` (DS) or `pret/pokeemerald` (GBA) directly into a Rust test oracle and asserting the engine matches it across a parameter grid (e.g. `calc_channel_volume_matches_pokediamond` in `devices/nintendo_ds/volume.rs`, `midi_key_to_freq_matches_pokeemerald` in `devices/gba/tables.rs`). When porting a new accuracy fix, add a transcription test rather than a recorded golden fixture.
- Each `optime-core` module has inline `#[cfg(test)]` unit tests (decoders, ADSR helpers, tuning, biquad, circular buffer, opcode interpreter).

## Conventions

- Idiomatic, zero-extra-dependency `std` in `optime-core`; keep it free of UI/audio/browser deps so both the app and the headless tests reuse it.
- Console-specific code belongs under `devices/<console>/`; it talks to the synthesis layer only through `SynthEvent`/`TickFeedback`. The synthesis layer never reaches into a device.
- Prefer making invalid states unrepresentable: enums over flag/int combinations (`SoundData`, `DevicePlayer`, `VoicePitch`, `ToneKind`, `Mp2kOp`, ADSR phases), `Option` over sentinels.
- Binary parsing uses `from_le_bytes` via the `util::read_*` helpers (return 0 on out-of-bounds rather than panicking).
- **Naming follows signal theory first.** Choose terminology so it matches its signal-processing meaning; in particular **"sample" always means one amplitude value at an instant (the sampling-theorem sense)** — that is the `Sample` (`= f64`) alias, `Frame` is a stereo `(Sample, Sample)`, and a whole decoded audio clip is a `Waveform` (never a "sample"). Reserve "sample" derivatives for genuine sampling concepts (`sample_rate`, a per-sample loop, PCM sample data, the "sampler"/"sampled" voice category vs PSG). When you rename a symbol on these grounds, **update the surrounding comments/doc-comments in the same pass** so the prose keeps saying "sample" only where an amplitude is meant.
- Keep `cargo clippy --workspace --all-targets` and `cargo fmt --all --check` clean.
- When touching synthesis math, check it against the matching pret decomp (pokediamond for DS, pokeemerald for GBA) and add/adjust a transcription unit test that pins the behavior to the C reference.

## Legacy app

`legacy-js/` holds the original browser app verbatim: `OptimePlayer/OptimePlayer.js` (engine + parser), `OptimePlayer/dsp.js`, `index.js` (DOM glue), `index.html`, plus the ffmpeg/canvas exporters `video-exporter.js` / `playlist-exporter.js` (intentionally **not** ported — the Rust app provides in-app WAV export instead). It is kept only as a historical reference (no longer the accuracy oracle). `demos/`, `assets/`, and `fonts/` remain at the repo root and are shared.
